# ตัวอย่างผลลัพธ์

## 1.ประเภทการส่งข้อความ

จากไฟล์ `RX_000001_6EA69BBA.txt` บันทึกหลักฐานการทำงานของระบบสื่อสารตั้งแต่ระดับเฟรมวิทยุ (KISS และ AX.25) ไปจนถึงการประกอบข้อมูล Telemetry และการตรวจสอบความถูกต้องครบทุกขั้นตอน โดยมีรายละเอียดแยกตามส่วนต่างๆ ดังนี้

**1. ชื่อไฟล์และบรรทัดเริ่มต้นเซสชัน (`START`)**

```text
2026-11-04T09:23:56.963+07:00 START id=0x6EA69BBA daily_receive=1 size=4 total=1 crc32=EEEA93B8 original_name="telemetry.txt"

```

* **วันและเวลา (Timestamp):** ทุกบรรทัดจะเริ่มต้นด้วยเวลาที่รับข้อมูลในระดับมิลลิวินาที (`2026-11-04T09:23:56.963+07:00`)


* **`id=0x6EA69BBA`:** รหัสประจำการส่งข้อมูล (Transfer ID) แบบสุ่ม 32-bit เพื่อใช้แยกเซสชันการส่งแต่ละครั้ง


* **`daily_receive=1`:** เป็นการรับข้อมูลครั้งที่ 1 ของวันนั้น ซึ่งตรงกับเลข `000001` ในชื่อไฟล์ `RX_000001_6EA69BBA.txt`


* **`size=4` และ `total=1`:** ข้อมูลที่ส่งมามีขนาดทั้งหมด 4 ไบต์ แบ่งการส่งออกเป็น 1 chunk


* **`crc32=EEEA93B8`:** ค่า Checksum มาตรฐาน CRC32 ของข้อมูลต้นทางที่ส่งมาพร้อมแพ็กเกจ `META` เพื่อใช้เป็นค่าอ้างอิงสำหรับตรวจเช็คเมื่อรับข้อมูลครบ


* **`original_name="telemetry.txt"`:** ชื่อไฟล์ต้นทางที่ระบุมาจากฝั่งส่ง (เมื่อผู้ส่งใช้คำสั่ง `--text` ระบบจะตั้งชื่อเริ่มต้นเป็น `"telemetry.txt"`)



**2. การพิสูจน์การถอดรหัสโปรโตคอล 3 ชั้น (`KISS_RAW`, `AX25`, `DATA`)**
ทุกครั้งที่ Arduino Mega ฝั่ง Ground Station รับแพ็กเกจได้สำเร็จ ระบบจะบันทึกข้อมูลแยกออกเป็น 3 บรรทัดคู่กันเสมอ เพื่อพิสูจน์การถอดรหัสจากนอกสุดเข้าไปหาข้อมูลข้างใน:

```text
KISS_RAW [DATA seq=0/1] len=45 unescaped=none hex=C0008EA49EAA9C88E086AA84A682A86103F043530102BA9BA66E0000000001000000040054455354F0996855C0
AX25     [DATA seq=0/1] dest=GROUND-0 src=CUBSAT-0 ctrl=0x03 pid=0xF0 valid=True header_hex=8EA49EAA9C88E086AA84A682A86103F0 full_ax25_hex=8EA49EAA9C88E086AA84A682A86103F043530102BA9BA66E0000000001000000040054455354F0996855
DATA     [DATA seq=0/1] id=0x6EA69BBA seq=0 total=1 len=4 payload_hex=54455354

```

* **บรรทัดที่ 1 `KISS_RAW` (ชั้นนอกสุดที่รับจาก HC-12):**
* `len=45`: ความยาวของเฟรม KISS ดิบรวม 45 ไบต์


* `unescaped=none`: ไม่มีไบต์พิเศษที่ต้องทำ Byte Unstuffing เนื่องจากในเฟรมนี้ไม่มีข้อมูลไบต์ใดตรงกับ `0xC0` หรือ `0xDB`


* `hex=C0 00 ... C0`: ข้อมูลเลขฐาน 16 ของเฟรม KISS ซึ่งเริ่มต้นด้วย `C0` (FEND เปิดเฟรม) ตามด้วย `00` (KISS Command Byte สำหรับ Data Frame บน Port 0) และปิดท้ายด้วย `C0` (FEND ปิดเฟรม)




* **บรรทัดที่ 2 `AX25` (ชั้นกลางหลังถอดกรอบ KISS `C0 00` และ `C0` ออก):**
* `dest=GROUND-0 src=CUBSAT-0`: ถอดรหัส Callsign ปลายทางและต้นทางจากการเลื่อนบิตกลับ (Bit-shifting) ได้ตรงตามที่กำหนดไว้


* `ctrl=0x03 pid=0xF0 valid=True`: ฟิลด์ Control เป็น `0x03` (UI Frame) และ Protocol ID เป็น `0xF0` (ไม่มีโปรโตคอล Layer 3) สถานะตรวจสอบผ่านถูกต้อง (`valid=True`)


* `header_hex=8EA49EAA9C88E086AA84A682A86103F0`: ส่วนหัวของ AX.25 ขนาด 16 ไบต์ แยกย่อยได้เป็น `8EA49EAA9C88E0` (`GROUND-0`), `86AA84A682A861` (`CUBSAT-0`), `03` (Control) และ `F0` (PID)


* `full_ax25_hex`: ข้อมูลเฟรม AX.25 ทั้งก้อน (ส่วนหัว AX.25 16 ไบต์ รวมกับ Application Packet ที่อยู่ข้างใน)




* **บรรทัดที่ 3 `DATA` (ชั้นในสุดหลังถอดส่วนหัว AX.25 และส่วนหัว Application ออก):**
* หากนำส่วนหัว AX.25 (16 ไบต์แรก) ออกจาก `full_ax25_hex` จะเหลือตัว Application Packet คือ `4353 01 02 BA9BA66E 00000000 01000000 0400 54455354 F0996855`


* ในส่วนหัว Application 18 ไบต์ประกอบด้วย `4353` (ตัวอักษร `"CS"`), `01` (เวอร์ชัน 1), `02` (ชนิดแพ็กเกจ `2 = DATA`, หากเป็น `01 = META`, `03 = END`), `BA9BA66E` (Transfer ID `0x6EA69BBA` แบบ Little-Endian), `00000000` (ลำดับ `seq=0`), `01000000` (จำนวนทั้งหมด `total=1`), `0400` (ความยาวข้อมูล `len=4`) และปิดท้ายหลังข้อมูลด้วย `F0996855` (CRC32 เฉพาะของแพ็กเกจนี้)


* `payload_hex=54455354`: ข้อมูลเนื้อหา (Payload) ล้วนๆ ที่แกะออกมาได้ โดยในแพ็กเกจ `[META]` ค่า `74656C656D657472792E747874` เมื่อแปลงเป็น ASCII คือชื่อไฟล์ `"telemetry.txt"` ส่วนในแพ็กเกจ `[DATA seq=0/1]` ค่า `54455354` เมื่อแปลงเป็น ASCII คือข้อความ `"TEST"` (54=`T`, 45=`E`, 53=`S`, 54=`T`)





**3. การยืนยันความถูกต้องของข้อมูล (`COMPLETE` และ `TEXT_UTF8`)**

```text
2026-11-04T09:23:58.082+07:00 COMPLETE crc32=EEEA93B8 expected_crc32=EEEA93B8 crc_match=True size=4 elapsed_seconds=1.118 file=payload_telemetry.txt
2026-11-04T09:23:58.082+07:00 TEXT_UTF8 "TEST"

```

* ทันทีที่รับก้อนข้อมูล `seq=0/1` ครบ ระบบนำไฟล์ที่ประกอบเสร็จแล้วมาคำนวณค่า CRC32 ได้เท่ากับ `EEEA93B8` ซึ่งตรงกับค่า `expected_crc32=EEEA93B8` ที่แจ้งมาใน `META` ทุกประการ (`crc_match=True`) ใช้เวลารับตั้งแต่ต้นจนจบเพียง `1.118` วินาที และบันทึกเป็นไฟล์ชื่อ `payload_telemetry.txt`


* บรรทัด `TEXT_UTF8 "TEST"` แสดงข้อความที่ถอดรหัสเป็นตัวอักษร UTF-8 ออกมาได้คือคำว่า `"TEST"`



**4. การส่งซ้ำเพื่อป้องกันข้อมูลสูญหาย (Redundancy Passes) และสถิติ (`GS_STAT` & `SESSION_CLOSED`)**

* **ใน Log จึงเห็นชุด `META` -> `DATA` -> `END` ซ้ำกัน 3 รอบ:** โปรแกรม `send.py` มีค่าเริ่มต้น `--passes 3` (ส่งซ้ำ 3 รอบ) โดยใน 1 รอบจะส่ง `META` 3 ครั้ง + `DATA` 1 ครั้ง + `END` 3 ครั้ง (รวมรอบละ 7 แพ็กเกจ)


* **`GS_STAT 21 0 0`:** รายงานสถิติจากบอร์ด Arduino Mega ฝั่ง Ground Station ทุกๆ 5 วินาที ตัวเลข 3 ตัวคือ `accepted=21` (รับแพ็กเกจผ่านสมบูรณ์ทั้ง 21 แพ็กเกจจาก 3 รอบการส่ง), `rejected_packet=0` (แพ็กเกจที่ AX.25 หรือ CRC ผิดพลาดเป็น 0) และ `rejected_kiss=0` (เฟรม KISS ที่เสียหายเป็น 0) พิสูจน์ว่าลิงก์วิทยุ HC-12 มีความแม่นยำ 100%


* **`SESSION_CLOSED status=COMPLETE received=1/1 duplicates=2`:** ปิดเซสชันการรับข้อมูลด้วยสถานะสมบูรณ์ (`COMPLETE`) ได้รับข้อมูลครบ `1/1` ก้อน และนับจำนวนแพ็กเกจ `DATA` ที่ส่งซ้ำตามมาในรอบที่ 2 และรอบที่ 3 ได้ `duplicates=2` โดยที่ระบบตรวจสอบแล้วว่าข้อมูลที่ส่งซ้ำตรงกับข้อมูลรอบแรกทุกไบต์

## 2.ประเภทรูปภาพ

จากไฟล์ `RX_000003_D9B9405B.txt` เป็นบันทึกการทดลองส่งไฟล์รูปภาพที่แสดงให้เห็นทั้ง **ข้อมูลไฟล์ภาพที่ถอดรหัสออกมาได้จริง** และ **สาเหตุที่การส่งไฟล์ขนาดใหญ่หยุดชะงักกลางคัน** โดยมีรายละเอียดในแต่ละส่วนดังนี้ (รูปนี้ส่ง 3 ครั้งถึงสามารถส่งได้ครบทุก chunk)

**1. ข้อมูลเริ่มต้นของไฟล์รูปภาพ (`START`)**

```text
2026-11-04T09:43:09.771+07:00 START id=0xD9B9405B daily_receive=3 size=77777 total=608 crc32=8DB69309 original_name="lamduan_bd2.jpg"

```

* **`daily_receive=3`:** เป็นการรับข้อมูลครั้งที่ 3 ของวันนั้น (`RX_000003`)


* **`original_name="lamduan_bd2.jpg"`:** ชื่อไฟล์ต้นทางคือรูปภาพ `lamduan_bd2.jpg`


* **`size=77777` และ `total=608`:** ไฟล์ภาพมีขนาด `77,777` ไบต์ (ประมาณ 75.95 KB) เมื่อนำมาหั่นเป็นก้อนละ 128 ไบต์ (`CHUNK = 128`) จึงแบ่งการส่งออกเป็นทั้งหมด **608 ก้อน** (ก้อนที่ `0` ถึง `606` ขนาดก้อนละ 128 ไบต์ และก้อนสุดท้ายขนาด 81 ไบต์)


* **`crc32=8DB69309`:** ค่า CRC32 ของไฟล์รูปภาพต้นฉบับทั้งไฟล์ที่ฝั่งรับต้องใช้ตรวจสอบเมื่อประกอบไฟล์ครบ 608 ก้อน



**2. การรับข้อมูลโครงสร้างไฟล์ (`[META]`)**

```text
KISS_RAW [META] len=67 unescaped=none hex=C000...C0
AX25     [META] dest=GROUND-0 src=CUBSAT-0 ctrl=0x03 pid=0xF0 valid=True ...
DATA     [META] id=0xD9B9405B total=608 size=77777 crc32=8DB69309 payload_hex=6C616D6475616E5F6264322E6A7067

```

* ฝั่ง Ground Station รับแพ็กเกจ `META` สำเร็จ 2 ครั้งติดต่อกัน (จากที่ส่งมา 3 ครั้ง) โดยเฟรม KISS มีความยาว `67` ไบต์


* ค่า `payload_hex=6C616D6475616E5F6264322E6A7067` เมื่อแปลงจากเลขฐาน 16 เป็นตัวอักษร ASCII จะได้คำว่า **`"lamduan_bd2.jpg"`** ตรงตามชื่อไฟล์ต้นฉบับ



**3. การรับข้อมูลเนื้อไฟล์รูปภาพ (`[DATA seq=1/608]`) และหลักฐานข้อมูลภาพ**

```text
KISS_RAW [DATA seq=1/608] len=169 unescaped=none hex=C000...3AF7FD1AC0
AX25     [DATA seq=1/608] dest=GROUND-0 src=CUBSAT-0 ctrl=0x03 pid=0xF0 valid=True ...
DATA     [DATA seq=1/608] id=0xD9B9405B seq=1 total=608 len=128 payload_hex=01000000...43616E6F6E0043616E6F6E20506F77657253686F74204733...323030343A30313A32312030393A31323A3130...

```

* **แพ็กเกจก้อนที่ 0 (`seq=0/608`) ตกหล่นกลางอากาศ** แต่ระบบรับก้อนที่ 1 (`seq=1/608`) เข้ามาได้สำเร็จ


* **ขนาดเฟรมใหญ่ขึ้น:** เนื่องจากส่งข้อมูลรูปภาพเต็มพิกัด `len=128` ไบต์ เมื่อรวมส่วนหัว Application (18 ไบต์) + CRC32 (4 ไบต์) + ส่วนหัว AX.25 (16 ไบต์) + กรอบ KISS (`C0 00` และ `C0` อีก 3 ไบต์) ขนาดของ `KISS_RAW` จึงเพิ่มขึ้นเป็น **169 ไบต์**


* **หลักฐานว่าเป็นข้อมูลจากไฟล์ภาพจริง:** หากแปลงค่า `payload_hex` ในบรรทัด `DATA [DATA seq=1/608]` เป็นข้อความ ASCII จะพบข้อมูล EXIF Metadata ของกล้องดิจิทัลที่ฝังอยู่ในส่วนหัวของไฟล์ JPEG ชัดเจน:


* `43616E6F6E` = **`Canon`**


* `43616E6F6E20506F77657253686F74204733` = **`Canon PowerShot G3`** (ชื่อรุ่นกล้องที่ใช้ถ่ายภาพนี้)


* `323030343A30313A32312030393A31323A3130` = **`2004:01:21 09:12:10`** (วันและเวลาที่ถ่ายภาพ)





**4. ทำไมการส่งภาพครั้งนี้ถึงไม่สำเร็จ (`GS_STAT`, `IDLE_TIMEOUT`, `INCOMPLETE`)**

```text
2026-11-04T09:43:14.051+07:00 GS_STAT	3	3	0
...
2026-11-04T09:43:41.991+07:00 IDLE_TIMEOUT received=1/608 missing=607 first_missing=[0, 2, 3, 4, ..., 20]
...
2026-11-04T09:44:09.709+07:00 GS_STAT	3	87	6
2026-11-04T09:44:11.962+07:00 SESSION_CLOSED status=INCOMPLETE received=1/608 duplicates=0

```

* **ความหมายของ `GS_STAT 3 87 6`:**
* เลขตัวที่ 1 (`accepted = 3`): บอร์ด GS Mega รับแพ็กเกจที่สมบูรณ์ผ่านเพียง **3 แพ็กเกจ** ตลอดการส่ง (คือ `META` 2 ครั้ง และ `DATA seq=1` อีก 1 ครั้ง)


* เลขตัวที่ 2 (`rejected_packet = 87`): มีแพ็กเกจวิ่งมาถึงบอร์ด GS Mega อีก **87 แพ็กเกจ** แต่ถูกปัดตกทั้งหมดเพราะข้อมูลบางไบต์เพี้ยนกลางอากาศ ทำให้เช็ค CRC32 หรือ AX.25 Header ไม่ผ่าน


* เลขตัวที่ 3 (`rejected_kiss = 6`): มีเฟรม KISS ที่บิตเพี้ยนตรงรหัส Escape หรือตัวปิดเฟรม `0xC0` จนโครงสร้างเฟรมพังไป **6 เฟรม**




* **`IDLE_TIMEOUT` และ `status=INCOMPLETE`:** เมื่อไม่มีแพ็กเกจที่สมบูรณ์ผ่านเข้ามาเพิ่มเกิน 30 วินาที โปรแกรมจึงแจ้งเตือนว่าขาดข้อมูลอีก 607 ก้อน (`missing=607` โดยก้อนที่ขาดคือ `0, 2, 3, ...`) และเมื่อหยุดโปรแกรมจึงปิดเซสชันด้วยสถานะ `INCOMPLETE` โดยเก็บไฟล์ที่รับค้างไว้เป็น `.part`
